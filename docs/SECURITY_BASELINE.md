# 安全基线 · 匿名回音

面向部署方与安全负责人，说明威胁模型、密码学设计、默认安全配置与上线检查清单。
**请在生产上线前完整阅读并逐项核对。**

---

## 1. 安全目标

1. 只有经准入（邀请码）的内部员工能进入系统。
2. 任何人（包括普通管理员、DBA、能读到数据库或备份的人）在**保险库封存期间无法把消息关联到具体员工**。
3. 只有在集齐 Shamir 门限 K 片、保险库解封时，才能做身份反查，且**每次反查强制审计**。
4. 消息原文不以明文落库；广播与历史只暴露归一化文本，降低写作风格去匿名化风险。

---

## 2. 威胁模型与边界

### 我们要防的

| 威胁 | 缓解措施 |
|---|---|
| DBA / 备份泄露直接看到"谁说了什么" | 消息原文与身份映射均为 AES-256-GCM 密文；密钥不在数据库 |
| 单名管理员或单名分片保管人私自溯源 | Shamir K/N 门限，单分片信息论上不泄露主密钥 |
| 从写作风格反推作者（标点/口头禅/句式） | 广播前语气归一化（LLM 或本地规则） |
| 匿名昵称被猜测/碰撞出真实身份 | 昵称随机生成、带 4 位混淆码、与用户表无明文外键 |
| 暴力破解弱密码 | scrypt 加盐哈希（含参数）、登录失败照常做哈希以缓解用户名枚举 |
| 邀请码被滥用 | 限次/限时、用后计数、一次性码 |
| 接口被刷 | 基于 Redis（降级内存）的每用户每分钟发送限流 |
| 越权访问管理接口 | JWT + `ADMIN_USERNAMES` 白名单；追责需 admin 且强审计 |
| 跨站携带 Cookie | HttpOnly、SameSite=Lax、生产 Secure；推荐同源部署 |

### 不在 M1 防护范围内（需知悉的残余风险）

- **内容本身自曝身份**：若用户写出"我是昨天请假的张三"，技术无法阻止，需在使用规范中提示。
- **元数据/流量分析**：IP、登录时间、在线状态可能辅助关联。M1 不做发送时间抖动/流量混淆。
- **解封期间的运行内存**：解封后主密钥存在进程内存，具备主机 root 或运行时内存转储能力的对手可获取。
  → 用后及时"封存"；生产主机需加固、最小权限、隔离部署。
- **本地规则归一化较弱**：`LLM_PROVIDER=off` 时只折叠机械标点指纹，无法改写句式。对去匿名化强度要求高时请配置 LLM。
- **单点追责审计不可抵赖性**：M1 审计存于同一数据库（追加写但管理员可删库）。高合规场景应把审计外发到只追加（WORM）日志系统。

## 3. 密码学设计

| 用途 | 算法 / 实现 |
|---|---|
| 消息原文加密 | AES-256-GCM（随机 96-bit IV，密文携带认证标签，防篡改） |
| 身份映射加密 | AES-256-GCM，主密钥经 HKDF-SHA256 按 purpose 派生子密钥（加密 / HMAC 分离） |
| 行定位 | `HMAC-SHA256(派生HMAC密钥, userId|alias)`，不存可直接关联的明文 ID |
| 主密钥分割 | GF(256) 上的 Shamir Secret Sharing，默认 K=2/N=3；单分片不泄露信息 |
| 登录密码 | Node `scrypt`（随机盐 + 存参数），拒绝明文/可逆存储 |
| 会话 | 自实现 HS256 风格签名 JWT（HMAC-SHA256），HttpOnly Cookie；另发短期 WS Token |

密钥分层：

```
Shamir 分片（N 份，离线分发）  ──合 K 片──▶ 保险库主密钥（仅内存）
                                                  │ HKDF(purpose)
                                  ┌───────────────┼────────────────┐
                              AES 派生密钥      HMAC 派生密钥
                                  │               │
                          identity_vault     lookup/alias 定位
MESSAGE_ENCRYPTION_KEY（env）──▶ 消息 AES-256-GCM（与保险库主密钥相互独立）
JWT_SECRET（env）──────────────▶ 会话签名
```

- 三类密钥**相互独立**：轮换其一不影响其余。
- 主密钥分片**绝不**写入镜像、环境变量（除显式的测试用 `VAULT_AUTO_UNSEAL_SHARES`）、数据库或日志。

## 4. 默认安全配置

- 容器以**非 root**（uid 10001）运行；只发布 app 端口。
- Postgres/Redis 不发布到宿主机，仅在内部 compose 网络可达。
- 生产强制要求 `JWT_SECRET` 与 `MESSAGE_ENCRYPTION_KEY`，缺失即启动失败。
- Cookie 生产环境 `Secure`；HttpOnly 防脚本读取；`SameSite=Lax`。
- 统一错误处理不向前端回传堆栈；认证错误用泛化文案。
- 全局请求体大小与消息长度上限（`MAX_MESSAGE_LENGTH` 默认 1000）。
- 响应头建议由前置代理补充：`Strict-Transport-Security`、`X-Content-Type-Options: nosniff`、
  `Referrer-Policy: no-referrer`、`frame-ancestors 'none'`。
- `noindex,nofollow`，避免被搜索引擎收录。

## 5. 上线检查清单（Checklist）

**密钥与分片**
- [ ] `JWT_SECRET` 为高熵随机值（`openssl rand -base64 48`），非默认/非示例
- [ ] `MESSAGE_ENCRYPTION_KEY` 为 32 字节 base64（`openssl rand -base64 32`）
- [ ] 已执行 `vault-cli init K N`，N 份分片已分发给不同保管人，**未**保存在服务器
- [ ] 生产 `.env` 中 `VAULT_AUTO_UNSEAL_SHARES` 留空（除非明确接受 PoC 风险）
- [ ] 已用 break-glass 流程演练过一次解封，确认分片可用

**访问控制**
- [ ] 修改 Postgres 密码，且与 `DATABASE_URL` 一致
- [ ] 仅最小集合用户名进入 `ADMIN_USERNAMES`
- [ ] 引导邀请码已轮换/限次；不再使用的码已停用
- [ ] Redis/Postgres 无对外端口；管理接口不直接暴露公网

**传输与网络**
- [ ] 强制 HTTPS/WSS，前置代理透传 WebSocket 升级头
- [ ] 仅内网/VPN 可达；或在网关层加 SSO/IP 白名单
- [ ] 已配置安全响应头

**数据与运维**
- [ ] 明确备份策略；备份加密离线存放，并验证"无密钥不可读"
- [ ] 明确解封/封存 SOP 与追责审批流程（谁、为何、何时能要求反查）
- [ ] 审计日志接入集中式/只追加存储（高合规要求）
- [ ] 确认语气归一化策略：高去匿名化要求场景配置 `LLM_PROVIDER=openai|ollama`
- [ ] 知悉第三方 LLM 的数据外发风险；敏感场景使用内网 Ollama 或可信私有网关

**运营约定**
- [ ] 公告告知参与者：内容不要自报姓名/可识别细节
- [ ] 规定追责必须填写真实事由并留存审批记录（系统已强制记录 `vault.reveal`）

## 6. 追责（Reveal）策略建议

- 反查接口 `POST /api/admin/reveal` 要求 `{alias, reason}`，缺事由直接 400。
- 每次调用写入审计（操作人、目标昵称、事由、时间），即使保险库封存导致失败也记录尝试。
- 建议制度：技术管理员只负责"执行"，发起追责需法务/HR/管理层中的独立授权，
  且门限分片由这些角色分别持有，使单人无法完成溯源闭环。
